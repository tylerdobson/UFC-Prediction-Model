# UFC Prediction Model: build roadmap

## Product and release target

Build a **pre-fight decision-support web app** for one operator. Before a UFC card, it should show verified matchups, calibrated win probabilities, current bookmaker quotes with their source times, the evidence behind each estimate, and whether a quote passes a conservative freshness and edge check. The operator decides whether to act and records any actual wager manually. The app never submits an order.

The first release is a polished, read-only **Streamlit** dashboard over the existing Python pipeline and SQLite database. It is a local/private release with five views: upcoming card, historical data, model evidence, data quality, and paper/actual ledgers. A hosted, multi-user service is a later option, not a prerequisite for the first useful product. See [WEB_APP_PLAN.md](WEB_APP_PLAN.md) and the editable [system diagram](UFC_SYSTEM_ARCHITECTURE.drawio).

**MVP:** One real UFC event can be imported, audited, scored with a trained model, checked against fresh pre-fight prices, displayed with provenance, and recorded in a capped paper ledger. Missing or stale evidence produces a clear `unavailable` or `pass` state. All work is reproducible from saved source snapshots and a documented runbook.

**Final version for this phase:** The MVP works repeatedly across events; historical evaluation and prospective paper results are visible alongside quote coverage, model calibration, unresolved settlements, and system health. No in-play alerts or automatic wagering are in scope.

## Design constraints

1. **Private and affordable by design.** Keep the GitHub repository private and the first deployment local. Choose data sources only after checking terms, redistribution rights, cost, quota, and reliability. Prefer a licensed, documented feed or reviewed CSV import. If historical prices are unaffordable, collect prospective quotes and paper-trade; do not manufacture historical returns from current lines.
2. **Trace every decision to a time and source.** Retain raw payloads and ingestion hashes. Store canonical fighter IDs plus explicit provider links, event/bout status, quote capture time, bookmaker update time, model feature cutoff, model version, and alert check time. A name match alone cannot merge fighters or silently pair odds with a bout.
3. **Prevent future-data leakage.** Rebuild historical features only from observations available before the target bout and decision cutoff. Use event-date ordered train, validation, and untouched test periods. Keep calibration on validation data and compare models with a bookmaker baseline on the same priced bouts.
4. **Fail closed on weak or stale evidence.** Do not show a bet candidate for an ambiguous matchup, incomplete card, cancelled or started event, missing or older-than-24-hour roster observation, missing price, mismatched snapshot, out-of-order timestamp, stale bookmaker update, or edge that disappears after the configured adverse price move. The current event start is only a conservative card-level proxy; obtain individual bout timing before claiming finer precision.
5. **Constrain exposure.** Paper stakes default to at most 1% of declared bankroll per bet and 5% per event. Freeze decision inputs and settle binary outcomes from verified results. Draws, no contests, voids, cancellations, and substitutions remain pending human review under the applicable bookmaker rules. Keep the manually entered actual-bet ledger separate. No auto orders or bookmaker account connection.
6. **Make uncertainty visible.** The interface must label sample size, quote coverage, calibration, model version, cutoff, source freshness, and missing data near each decision. Show `pass` and `unavailable` as normal outcomes. Do not present expected value or a small-sample positive ROI as a guarantee.
7. **Keep the interface read-only and legible.** The dashboard reads stored, already audited results; ingestion, training, and settlement run outside page requests. Use clear status labels and accessible contrast, responsive tables, and an obvious UTC/local time label. The UI must not expose API keys or present an order button. Secrets stay in server-side environment configuration, never in Git, browser code, reports, or logs.

## Event-day operating loop

1. **Before the card:** Import the latest dated roster and statuses; review substitutions and confirm the known UTC card start. Keep the source payload and run receipt.
2. **Before scoring:** Run the read-only evidence integrity command, then `ufc-model audit`. Resolve critical identity, result, and timing issues; mark any incomplete bout unavailable. Refresh the dated roster if its observation is over 24 hours old.
3. **At the decision time:** Run `ufc-model alert-event EVENT_ID` with the chosen model and configured freshness/price-drift thresholds. It fetches a new odds snapshot, scores the card, and prints the gate outcome. The operator rechecks the market when acting because a displayed quote is not executable proof.
4. **Paper record:** Run `ufc-model paper-trade EVENT_ID --bankroll-units AMOUNT` with the same gate thresholds. It refreshes prices and records only accepted decisions with the declared bankroll and caps. Inspect the persisted gate checks, model cutoffs, prices, and rejection reasons. This is a separate snapshot from a preceding `alert-event` call; the displayed market still needs a human recheck before any actual wager.
5. **After results:** Import verified results, rerun the audit, and settle binary paper decisions. Review nonbinary outcomes manually. If an actual bet was independently placed, enter the accepted odds, stake, and bookmaker settlement through the separate CLI ledger.
6. **Post-event review:** Record source failures, quote latency, unmatched bouts, calibration and realized returns. Use these observations to decide whether the next model or source version earns promotion.

## Deployment and observability

Start with one local operator, SQLite, a Python virtual environment, and Streamlit reading the same local database. Keep the database, raw snapshots, model artifacts, reports, backups, and credentials outside Git. Add a repeatable runbook, pinned dependencies, DB migration/backup/restore commands, and a manual fallback for failed imports. Only add PostgreSQL, FastAPI, authentication, and a worker queue when shared users or concurrent scheduled jobs justify them.

Track each ingestion run's source, status, fetched time, row counts, unmatched items, and payload hash; each model run's version, feature cutoff, sample counts, and evaluation metrics; each odds check's bookmaker update/capture age and rejection reason; and each ledger's open exposure and pending settlements. Surface the most recent successful run and data age in the dashboard. A failed source fetch, stale card, missing prices, or unresolved audit error should leave the previous record intact and clearly block new recommendations rather than silently producing an empty or apparently fresh card.
